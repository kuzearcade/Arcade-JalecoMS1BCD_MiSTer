# Checkpoint — 2026-09-23

Where the core stands after 52 commits over four days (2026-09-20 to
2026-09-23, `271406a` to `c6e2160`). This is a snapshot, not a plan: see
`docs/PLAN.md` for the milestones and `docs/known-issues.md` for the full
record of every defect, closed and open.

## What runs

**All 16 shipped sets boot and run on a DE10-Nano** — System B 7 of 7,
System C 7 of 7, System D 2 of 2 — from one bitstream. Nothing in the RBF is
per-game: the `.mra`'s game-mode byte (third `<switches>` byte) carries the
board type `[1:0]`, sample clock `[4]`, protection model `[6:5]` and autofire
unlock `[7]`, and the memory map, video layout, interrupt model and I/O all
follow from it.

Latest bitstream: **28,897 / 41,910 ALMs (69 %), 544 / 553 M10K (98 %), 0
timing violations**, md5 `083e0f10313e8e039a7144b149fe5e7c`, deployed to the
board as `Arcade-JalecoMS1BCD_20260923.rbf`.

M10K is the binding constraint at 98 %. Anything new that needs block RAM
needs something else to give it back first.

## Closed this session

- **MS1-56** — System D had no memory map and fell into System B's.
- **MS1-57** — the tile-fetch lookahead wrapped on the visible width, not the
  line: eight wrong pixels at the start of every line, on the SDRAM path
  only, invisible to every gate because the gates run the reference harness.
- **MS1-58** — the sim Makefiles did not depend on the RTL Verilator finds
  through `-y`, so a correct fix could measure the bug it had just fixed.
- **MS1-59** — every game showed a five-pixel strip down the left of the
  screen. Board shift 5 px → 0 px, 0 differing pixels.
- **MS1-60** — the sprite pass overran blanking by ~15 rows and the beam read
  the plane while it was still being drawn: 212,970 clk against a 165,888 clk
  budget, now 151,372.
- **MS1-61** — `ss_hold` froze `ymdiv` through the savestate replay, so three
  of its four phases made `ym_cen_p1` dead and the YM register replay stalled
  forever; `rp_run` then had no clear but "all 256 done" and latched high,
  holding jt51's write strobe for the rest of the session.
- **MS1-62** — the YM2151 register shadow decided select-vs-data from a "last
  write anywhere on the bus" latch, read one write late. The sound driver's
  YM access is a subroutine, so a `JSR` pushed a return address in between and
  every write in the game landed in `ymsh[0]`. The replay then wrote 255 zeros
  over the chip's live registers, stopping the timer the driver uses as its
  only timebase.
- **MS1-32** — closed as a misdiagnosis of MS1-57: right measurement, wrong
  cause.

## Lessons this session paid for

**A harness that always parks on the same phase cannot see a phase-dependent
bug.** `sim/rtl/ms1_frames` raised `ss_freeze` at an arbitrary tick while the
real engine waits for a vblank edge, so it always landed on the one `ymdiv`
value that worked, reported "replay done" three times, and a correct
diagnosis was retracted on that evidence. It now parks on the vblank edge and
takes `MS1_SS_YMDIV=N` to force the phase.

**A sound bug needs the sound harness.** 64th Street's sound CPU makes zero
chip writes in `sim/rtl/ms1_frames` at frame 200, before any savestate, so
that harness was never going to answer MS1-62. `sim/rtl/ms1_snd` reaches the
driver's steady state in seconds and now runs the savestate sequence itself
(`MS1_SS_AT`, `MS1_TRACE_FROM`).

**The failed verification of a correct fix looks exactly like a wrong
diagnosis** (MS1-58). Check that the binary rebuilt before believing the
measurement.

## Savestate compatibility

States written before `c6e2160` cannot be recovered: their YM shadow never
held the chip's registers, so a load has nothing true to replay and the sound
driver stops. States written after it restore correctly.
